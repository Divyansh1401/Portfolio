## Findings — defects in files this task does not own (both FIXED, see top)

Per the task's scope rules, these were **not edited** (only
`app/test/a11y.test.mjs`, `app/test/a11y/`, and this doc are owned by
TASK L3b). Fix ownership belongs to whoever owns `create.page.js` /
`create.html` / `bouquet.html`.

### 1. Chip "radiogroups" have no arrow-key navigation

**File:** `app/client/create.page.js` (mode chips ~lines 96–133, shape chips
~lines 137–163). Related markup: `app/pages/create.html`
(`#mode-group`, `#shape-group`, both `role="radiogroup"`).

**Problem:** Each chip is a `<button role="radio">`, but there is no
`keydown` handler anywhere in `create.page.js` for either group. Per the
[ARIA APG radio-group pattern](https://www.w3.org/WAI/ARIA/apg/patterns/radio/),
a `role="radiogroup"` is expected to support ArrowLeft/ArrowRight (and
typically ArrowUp/ArrowDown) to move focus *and* selection between its
radios, with only the checked radio in the Tab order (roving `tabindex`).
Today: every chip has its native default tabindex, so Tab does visit each
one individually (that part of the flow — the order checked in test 6 —
is fine), but the arrow keys do nothing at all; a keyboard user must Tab
through every chip in a group one at a time to reach the flower or shape
they want, and there is no way to jump directly with the arrow keys the
`role="radio"` semantics imply screen-reader users will try.

**Repro:** `node --test app/test/a11y.test.mjs` → tests 7 and 8
("arrow keys move selection within the flower/shape radiogroup") fail:
focus and `aria-checked` are unchanged after `ArrowRight`.

**Suggested fix (for whoever owns `create.page.js`):** add a `keydown`
listener on each `chip-row` that, on ArrowLeft/ArrowRight (wrapping),
moves focus to the adjacent chip *and* calls the existing `selectMode` /
`selectShape`, and sets `tabindex="-1"` on every chip except the checked
one (`tabindex="0"`) so Tab enters/leaves the group in one stop, matching
the ARIA APG pattern. `selectMode`/`selectShape` already do everything
else needed (update `aria-checked`, the hero preview, and persist the
draft) — the fix is purely the keydown wiring + roving tabindex, no new
state.

### 2. `bouquet.html` (the recipient page) has no `<h1>`

**File:** `app/pages/bouquet.html`.

**Problem:** The page has no heading element at all — `.bq-hint`,
`.bq-message__text` etc. are all plain `<p>`s, and the only text before
reveal is inside the hint span ("Hold to open" / "Scroll to open"), which
is `aria-hidden="true"` besides. A recipient following a bare `/b/<id>`
link (this is the very first page they land on, cold) has nothing that
identifies the page to assistive tech — a screen-reader user landing here
gets no page-level orientation at all until (if) they find their way to
the message.

**Repro:** `node --test app/test/a11y.test.mjs` → test 2
("/b/:id (bouquet.html): title, lang, one h1, labelled controls") fails:
`h1` count is 0.

**Suggested fix (for whoever owns `bouquet.html`):** add a visually
unobtrusive `<h1>` (can be visually hidden with a standard
`.sr-only`/clip pattern if a heading doesn't fit the design, e.g. "A
bouquet for you") near the top of `#bq-root`, matching the `<title>`
text. `create.html` and `sent.html` both already do this correctly and
were not flagged.
